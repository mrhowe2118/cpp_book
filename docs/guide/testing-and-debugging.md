# 测试与调试

**"样例过了"是最不可靠的结论。** 这一节给你一套方法：不靠"再看一遍"，而是用数据说话。

## 本节学会什么

- 建立三层测试习惯：样例 → **手造边界** → 对拍
- 学会用 `cerr` 打印中间值定位问题（而且不污染答案文件）
- 掌握"缩小数据"和"二分注释"两种快速定位法
- 拿到一张"看到 CE / WA / RE / TLE 该往哪查"的对照表

## 为什么需要它

看一段**样例全过**的代码：

> 求 n 个数中的最大值。

```cpp
int mx = 0;                        // ← 问题就在这一行
for (int i = 0; i < n; i++) {
    cin >> x;
    if (x > mx) mx = x;
}
```

用题目给的样例（都是正数）测，完全正确。
但**如果输入全是负数呢？**

::: exam 样例只验证了一种情况
样例通常是出题人**精心挑的**一个普通情况。它验证不了：

- 边界（`n = 1`、最大值、空）
- 特殊值（全负数、全相同、0）
- 多组数据之间的互相影响

**所以"样例过了"只是最低门槛，不是通关证明。**
:::

## 最小可运行示例：一个真实的边界 bug

<!-- expect
3
-5 -2 -9
---
0
-->
```cpp
#include <cstdio>

int main() {
    int n;
    scanf("%d", &n);

    int mx = 0;                 // ✗ 初值取 0，可所有数都是负数时它就成了"最大值"
    for (int i = 0; i < n; i++) {
        int x;
        scanf("%d", &x);
        if (x > mx) mx = x;
    }

    printf("%d\n", mx);
    return 0;
}
```

输入三个负数 `-5 -2 -9`，最大值应该是 **`-2`**。
程序输出的是 **`0`**——因为 `mx` 一开始就是 0，而所有输入都没超过它。

### 修好它：两个正确写法

<!-- expect
3
-5 -2 -9
---
-2
-->
```cpp
#include <cstdio>

int main() {
    int n;
    scanf("%d", &n);

    int mx;                      // 先读第一个数，用它当初值
    scanf("%d", &mx);
    for (int i = 1; i < n; i++) {
        int x;
        scanf("%d", &x);
        if (x > mx) mx = x;
    }

    printf("%d\n", mx);
    return 0;
}
```

::: range 打擂台的两种初值写法
| 写法 | 优点 | 缺点 |
| --- | --- | --- |
| **先读第一个数当初值**（上面这种） | 永远正确，不依赖数据范围 | 输入格式要处理一下 |
| 取一个"绝对够小/够大"的值 | 代码更短 | **要保证数据不会超过它** |

```cpp
const int INF = 1e9;            // 如果题目保证 |a[i]| ≤ 10^9
int mx = -INF;                  // ✓ 比任何可能的值都小

// 求最小值时反过来
int mn = INF;
```

**⚠️ 用常量初值时必须确认题目范围。** `mx = 0` 错就错在"想当然认为数都是正的"。
:::

## 关键过程与易错点

### 一、三层测试：从便宜到贵

```text
第 1 层：跑样例                  ← 必须做，但远远不够（10 秒）
第 2 层：手造边界数据             ← 性价比最高（1 分钟）
第 3 层：对拍（随机数据自动比对）  ← 最可靠，但成本高（15 分钟）
```

::: exam 第 2 层被严重低估
**手造边界数据只要 1 分钟，却常常能发现一半的错误。**

每道题写完，至少造这五组：

| 造什么 | 为什么 |
| --- | --- |
| **最小规模**（`n = 1`） | 循环、相邻比较、去重最容易在这里挂 |
| **最大值** | 溢出、数组越界、超时 |
| **全部相同** | 去重、统计 |
| **包含 0 / 负数** | 初值、除法、取余 |
| **题目提到的特殊情况** | "无解"、"只有一组" |

**把这份清单背下来，写完每道题都过一遍。**
:::

### 二、打印调试：`cerr` + 带上变量名

**在关键位置打印中间值**是最直接的调试手段。但有两个细节：

**细节 1：用 `cerr`，不要用 `cout`**

<!-- expect
2
-->
```cpp
#include <cstdio>

int main() {
    int a = 7, b = 3;

    // stderr：只打到屏幕，不会进答案文件
    fprintf(stderr, "调试：a=%d b=%d\n", a, b);

    printf("%d\n", a / b);   // stdout：这一行才会进答案文件
    return 0;
}
```

上面这段程序的 stdout **只有 `2`**——调试信息跑到屏幕上去了。
如果你用 `printf` 或 `cout` 打调试信息，它会混进答案文件，直接判 WA。

上面用的是 C 风格的 `fprintf(stderr, ...)`。C++ 里对应的是 `cerr`：

```cpp
cerr << "调试：a=" << a << " b=" << b << '\n';   // 只进屏幕，不进答案文件
```

**细节 2：打印时带上变量名**

```cpp
cerr << "i=" << i << " sum=" << sum << '\n';      // ✓ 一眼知道哪个是哪个
cerr << i << " " << sum << '\n';                   // ✗ 三个数不知道谁是谁
```

::: pitfall 调试输出交卷前必须删掉或注释
虽然 `cerr` 不进答案文件，但：

- 它**拖慢程序**（大量调试输出可能让你 TLE）
- 如果误用了 `cout`，就会**污染答案文件**

**纪律：调试信息用 `cerr`，交卷前全局搜索一遍删掉。**

搜索关键词：`cerr`、`stderr`、`dbg`。
:::

### 三、定位法一：缩小数据

数据一大，错在哪就看不出来了。**把数据缩小到能在纸上手算**：

```text
原始：n = 100000，答案错了
      ↓ 改小（或改生成器）
n = 5 的一组数据 → 手动算一遍 → 和程序输出对照 → 找到出错的那一步
```

**具体做法**：把输入改成几个数，然后**一步步 `cerr` 打印**，看哪一步开始和你的手算不一致。

::: exam 手算能力是调试能力的一半
**能在纸上一行一行算出正确答案的人，调试速度是别人的好几倍。**

因为你有了"标准答案"，程序在哪一步偏离，你立刻就知道。
:::

### 四、定位法二：二分注释

不确定是哪一段出的错时，**把代码切成两半，先确认错在哪一半**：

<!-- no-compile -->
```cpp
int main() {
    // ---- 第一部分：读入 + 处理 ----
    ...

    cerr << "检查点 A：处理完了，sum = " << sum << '\n';   // 打点

    // ---- 第二部分：输出 ----
    ...
}
```

在中间打几个"检查点"，看**第一个和预期不符的检查点**在哪，
错误就在它和上一个检查点之间。

**这叫"打点法"，是工程里最常用的调试手段。**

### 五、看到评测结果，该往哪查

| 结果 | 先查什么 | 常见原因 |
| --- | --- | --- |
| **CE** | 编译报错的**第一条** | 少分号、全角标点、缺 `#include` |
| **WA** | 输出格式 → 边界 → 类型 | 末尾空格、没测 `n=1`、溢出 |
| **RE** | 数组大小、下标、除零 | 数组开小、越界、递归太深 |
| **TLE** | 数一数循环跑了多少次 | 复杂度不达标、死循环 |
| **MLE** | 算一算数组占多少 MB | 数组开太大（按**声明**算） |

::: pitfall RE 最难查，因为"有时崩有时不崩"
数组越界**不一定立刻崩**——它可能只是悄悄改掉别的变量。

所以看到"同一份代码，有时 RE 有时 WA"，**第一反应就该是"越界了"**。

用 `assert` 帮你抓出来：

```cpp
#include <cassert>

for (int i = 1; i <= n; i++) {
    assert(i < MAXN);         // 越界时立刻停下来，并告诉你哪一行
    sum += a[i];
}
```

**注意**：定义 `NDEBUG` 时 `assert` 会被跳过（有些评测环境会这么编译），
所以 `assert` 是**调试工具**，不能当正式的错误处理。
:::

### 六、调试的心态：不要猜

::: exam 三种"猜"，三种浪费时间
| 你是不是这样 | 正确做法 |
| --- | --- |
| "我觉得是这里错了，改一下试试" | **先打印，确认它真的错了** |
| "再改一处，应该就好了" | **一次只改一个地方** |
| "看起来没问题啊，再看一遍" | **造一组能暴露问题的数据** |

**调试的本质是"用数据缩小范围"，不是"灵光一现"。**
:::

## 动手检查

1. 把上面那个 `mx = 0` 的 bug 复现出来，然后用"全是负数"的数据测——这就是手造边界。
2. 给一段你写的代码加上 `cerr` 检查点，运行后确认：调试信息在屏幕上，答案文件里没有。
3. 故意写一个数组越界，用 `assert` 抓它，看报错信息里有没有行号。
4. 拿你以前一道 WA 的题，**只做一件事**：测 `n = 1`、全相同、最大值这三组。
   记录你发现了什么。

::: pitfall 这一节是"元能力"
测试与调试不是某个知识点，**它作用在你写的每一道题上**。

这里给的清单建议你抄成一张卡片：

```text
写完一题，先过这五组数据：
□ n = 1        □ 最大值      □ 全相同
□ 含 0 / 负数   □ 题目提到的特殊情况
```

**这张卡片能救的分，比多学一个算法多。**
:::
