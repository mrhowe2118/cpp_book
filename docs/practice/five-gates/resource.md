# 资源关：MLE / RE / TLE

::: gate 第 5 关 · 资源关
**前四关都过了，程序跑出了正确答案——但它用了 3 秒，或者开了 400 MB 内存。**

时间、内存、栈，三个限制任何一个不达标，这道题一样是 0 分。
而且这一关里有一条**完全违反直觉**的规则：内存是按**声明**算的。
:::

## 本节学会什么

- 学会给数组"算账"：多少个元素 × 几个字节 = 多少 MB
- 理解 **MLE 按声明的空间计算**，而不是按实际使用
- 知道为什么**大数组必须开在全局**（栈空间）
- 认出 RE / TLE / OLE 各自的典型原因

## 为什么需要它

前三关失败时，你会很明确地知道"我错了"。这一关不一样：

> 程序**跑出了完全正确的答案**，只是花了 1.8 秒。
> 时间限制是 1 秒。这道题 0 分。

结果对了但分数没来，这比算错更让人难受。而它的成因往往是**一行声明**或者**一次没必要的重复计算**。

::: exam 这一关的分档特性
资源关的失败常常**只影响一部分测试点**：

| 情况 | 后果 |
| --- | --- |
| 小数据能过、大数据超时 | 拿到部分分 |
| 数组开小，大测试点越界 | 部分点 RE |
| 内存声明超标 | **所有点 MLE，整题 0 分** |

**注意最后一行**：内存超限是按声明算的，所以哪怕小数据也一起挂掉。
:::

## 最小可运行示例：给数组算账

内存 = **元素个数 × 每个元素的字节数**。

<!-- expect
400
40
24
-->
```cpp
#include <iostream>
using namespace std;

int main() {
    // 只看"声明了多少"，不看实际用了多少
    cout << sizeof(int) * 100000000 / 1024 / 1024 << '\n';        // int  a[1e8]
    cout << sizeof(int) * 10000000 / 1024 / 1024 << '\n';         // int  a[1e7]
    cout << sizeof(long long) * 3000000 / 1024 / 1024 << '\n';    // long long a[3e6]
    return 0;
}
```

输出（单位：MB）：

```text
400
40
24
```

::: range 开数组前先算一遍
| 写法 | 占用 | 结论 |
| --- | --- | --- |
| `int a[1000]` | 4 KB | 随便开 |
| `int a[100000]`（10⁵） | 400 KB | 安全 |
| `int a[1000000]`（10⁶） | 4 MB | 安全 |
| `int a[10000000]`（10⁷） | 40 MB | 谨慎，看内存限制 |
| `int a[100000000]`（10⁸） | **400 MB** | **基本一定 MLE** |
| `long long a[10000000]` | **80 MB** | 比 `int` 贵一倍 |
| `int a[1005][1005]` | 约 4 MB | 二维数组涨得很快 |

**常用换算**：`int` 1 个 = 4 字节，`long long` = 8 字节，`double` = 8 字节，`char` = 1 字节。
:::

## 关键过程与易错点

### 一、MLE 按声明算，不按实际使用算

这是本节最反直觉的一条：

```cpp
#include <iostream>
using namespace std;

int a[100000000];     // 声明了 400 MB

int main() {
    a[0] = 1;         // 实际只用了 4 个字节
    cout << a[0] << '\n';
}
```

**程序只用了 4 个字节，但评测机按 400 MB 算，直接 MLE。**

原因：全局数组是在程序启动时就分配好整块空间的。**你声明了多大，它就占多大。**

::: pitfall 调试时也别乱开数组
有的同学喜欢把数组开到 `1e8` "以防万一"。结果：

- 本地跑得动（你的电脑内存大）
- 评测机直接 MLE

**按题目的最大数据范围开，再多加 5～10 个位置，就足够了。**
:::

### 二、栈空间：为什么大数组要开在全局

函数内部的局部变量放在**栈**上，而栈空间是**有限**的：

```cpp
int main() {
    int a[1000000];   // 4 MB，开在栈上
}
```

| 位置 | 在哪 | 能开多大 |
| --- | --- | --- |
| 函数内部（局部） | **栈** | 受栈空间限制，开大了直接 RE |
| 函数外部（全局） | **静态存储区** | 受总内存限制，能开得大得多 |

::: exam 一条能救命的习惯
**所有可能变大的数组，一律开在全局。**

```cpp
const int MAXN = 100005;
int a[MAXN];          // ✓ 全局

int main() {
    // int a[MAXN];     // ✗ 局部，别这么写
}
```

理由：评测机的**栈空间通常就等于题目的内存限制**，而且局部数组还要和你所有局部变量抢这块空间。
一旦栈溢出，程序直接 RE——而且它**不会给你编译错误**，只在运行时崩。

**递归也要注意**：递归深度大时，每一层都在栈上占空间。递归爆栈属于同一类问题。
:::

### 三、RE：运行时错误

RE 是"程序崩了"。常见原因：

| 原因 | 典型症状 | 改法 |
| --- | --- | --- |
| **数组越界** | 大测试点崩、小数据正常 | 数组开够，下标别超 |
| **除以 0** | 某个测试点崩 | 判断分母，特判 |
| **取模的模为 0** | 崩 | 检查取模参数 |
| **递归太深爆栈** | 大数据崩 | 减少递归深度，或改递推 |
| **空指针解引用** | 崩 | `freopen` 后检查返回值 |
| **`vector` 访问越界** | 崩 | 用 `at()` 调试，或检查 `size()` |

::: pitfall 数组越界"不一定立刻崩"
越界写可能只是**悄悄改掉旁边的变量**，程序继续跑，结果错得莫名其妙。

它也可能在读越界时崩——取决于那块内存刚好有没有被用。
**所以越界是"随机惩罚"：同一个 bug，有时 RE，有时 WA。**
:::

### 四、TLE：超时

超时的两种成因，先分清是哪一种：

| 类型 | 表现 | 原因 |
| --- | --- | --- |
| **复杂度不达标** | 大数据超时，小数据秒过 | 算法复杂度不够 |
| **常数太大 / 死循环** | 连样例都要很久 | `cin/cout`、`memset`、死循环 |

**复杂度的判断**见 [数据范围表就是给分表](/practice/data-range)：`1 秒 ≈ 10⁸ 次简单运算`。

几个常见的"常数杀手"：

| 写法 | 问题 | 改法 |
| --- | --- | --- |
| 循环里 `cin >> x` 十万次以上 | `cin` 比 `scanf` 慢 | 加 `ios::sync_with_stdio(false); cin.tie(0);` 或用 `scanf` |
| 多组数据里 `memset` 整个大数组 | 每组都清 10⁷ 个元素 | 只清用到的那一段（`memset(a, 0, (n+1)*sizeof(int))`） |
| 循环里反复调用 `strlen` | 每次都重算长度 | 提前存进变量 |
| `vector` 反复 `push_back` 不 `reserve` | 反复扩容 | 先 `reserve(n)` |
| 死循环 | 循环变量不收敛 | 检查 `while` 的边界推进 |

::: pitfall 用 `memset` 清大数组也有代价
`memset(a, 0, sizeof(a))` 在 `n` 只有 10 的时候也会清完整个数组。
如果数组开了 10⁷、又有 10⁵ 组数据——那就是 10¹² 次操作，必超时。

**按需清空**：

<!-- no-compile -->
```cpp
memset(cnt, 0, (n + 1) * sizeof(int));   // 只清用到的那一段
```
:::

### 五、OLE：输出超限

OLE（Output Limit Exceeded）的成因基本只有一个：**输出太多**。

- 调试输出忘了删（尤其写在循环里的 `cout`）
- 死循环不停输出
- 输出了整个数组而题目只要一个数

::: exam 交卷前的资源关清单
- [ ] **所有大数组都开在全局**，没有写进 `main` 里
- [ ] 数组大小按题目**最大**范围开，多留 5～10 个位置
- [ ] 算过一遍内存：会不会超过限制？（`int` 4 字节 / `long long` 8 字节）
- [ ] 复杂度和数据范围**对得上**（不会 O(n²) 去跑 10⁵）
- [ ] 多组数据清空是**按需**清的，没有每组 `memset` 整个大数组
- [ ] **调试输出全部删掉**（`cout`、`printf` 写的中间结果）
- [ ] 二分、双指针、`while` 循环都检查过**一定会收敛**
- [ ] `freopen` 有返回值检查（至少调试时要有）
:::

## 动手检查

1. 用 `sizeof` 算一下你常用数组的实际占用（和上面的示例一样），列一张你自己的"安全尺寸表"。
2. 写一个在 `main` 里开 `int a[1000000]` 的程序，本地运行看看会不会崩；
   再把它改成全局，对比差异。（本地可能不崩，但评测机会。）
3. 写一个 `n = 1` 时除以 0 的程序，观察本地和评测机的反应差别。
4. 检查你以前提交的代码里，有没有**在循环里输出调试信息**的地方。
