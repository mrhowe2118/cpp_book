# 文件关：freopen 第一大现场

::: gate 第 3 关 · 文件关
**复赛的第一大失分现场。** 算法全对、代码全对，只是读错了文件——单题 0 分。

这一关的特点是：**错一个字符，代价是一整道题。**
:::

## 本节学会什么

- 背下一个**永远不会写错的 `freopen` 模板**
- 认出 10 种典型的文件关错误，知道每种长什么样
- 理解为什么"本地能跑、交上去输出为空"
- 拿到一份文件名自查清单

## 为什么需要它

复赛和平时刷题有一个根本区别：

| | 平时刷题（洛谷在线提交） | 复赛（第二轮机试） |
| --- | --- | --- |
| 输入从哪来 | 标准输入（键盘/评测管道） | **文件** `apple.in` |
| 输出到哪去 | 标准输出（屏幕） | **文件** `apple.out` |
| 谁负责重定向 | 评测机 | **你的代码自己** |

平时你写 `cin >> n;` 就能读到数据，因为评测机帮你接好了管道。
**复赛没有这个管道**——你要自己用 `freopen` 把文件接到 `stdin` / `stdout` 上。

没接，或者接错了，程序读到的就是空数据：**算法再对，输出也是错的或空的。**

::: exam 这一关为什么排第三
按经验，文件关是复赛失分最集中的一关。它同时具备三个特征：

1. **错的方式极多**（文件名、路径、标点、位置……）
2. **本地往往测不出来**（很多人在本地就注释掉了 `freopen`）
3. **代价是整道题**

所以它值得你花最多的时间在这里。
:::

## 最小可运行示例

标准的复赛写法：

```cpp
#include <cstdio>
#include <iostream>
using namespace std;

int main() {
    freopen("apple.in", "r", stdin);    // 把 apple.in 接到标准输入
    freopen("apple.out", "w", stdout);  // 把 apple.out 接到标准输出

    int a, b;
    cin >> a >> b;
    cout << a + b << '\n';

    return 0;
}
```

四行代码，四个关键点，每一个都可能出错：

| 组成 | 含义 | 错了会怎样 |
| --- | --- | --- |
| `"apple"` | **题目规定的文件名**，必须逐字符一致 | 打不开文件，读到空数据 |
| `"r"` | 读模式（read） | 写反而会清空文件 |
| `"w"` | 写模式（write） | — |
| `stdin` / `stdout` | 接的目标 | 接反了，或者接成 `stderr` |

::: pitfall `freopen` 与 `std::cin` 混用没问题，但要注意顺序
`freopen` 之后 `cin` / `cout` 会自动走文件，**这正是我们要的效果**。

但如果你同时用了 `ios::sync_with_stdio(false)`，在**某些环境**下可能出现输出为空——
两者都动了 C 和 C++ 的输入输出缓冲，混用有风险。

**保守做法：复赛模板里不要写 `ios::sync_with_stdio(false)`，或者不要用 `freopen` 之外的缓冲操作。**
两种方案二选一，别都上。
:::

## 关键过程与易错点

### 十个真实现场

每题按"症状 → 原因 → 改法"写，**对照自己的模板逐条检查**。

#### 错误 1：忘写 `freopen`

**症状**：本地跑得好好的，交上去 0 分，或者答案全错。
**原因**：本地测试时注释掉了 `freopen`，忘了改回来。
**改法**：**本地测试也要用文件**。把测试数据写成 `apple.in`，让本地和考场完全一致。

#### 错误 2：文件名拼错或大小写不对

**症状**：单题 0 分。
**原因**：题目要求 `apple.in`，你写了 `Apple.in`、`appel.in`、`apple.txt`。
**改法**：**复制粘贴**题目里的文件名，不要手打。复制后逐字符核对。

#### 错误 3：代码与题目错位

**症状**：某一题 0 分，其他题正常。
**原因**：你复制了上一题的框架，**文件名和 `freopen` 没改**：
`detect.cpp` 里读的却是 `duel.in`。
**改法**：每开一题，先改三处——**源文件名、`freopen` 的两个文件名、输出格式**。

#### 错误 4：中文全角标点

**症状**：编译直接报错，或者找不到文件。
**原因**：`freopen("apple。in", ...)` —— 中间的 `.` 是全角句号，或者引号是全角引号。
**改法**：把这一行删掉，切英文输入法重打。

#### 错误 5：路径前缀写成 Windows 风格

**症状**：本地能跑，评测机编译就错，或者运行时打不开文件。
**原因**：写了 `freopen(".\\apple.in", "r", stdin)`。
**注意**：在 C++ 字符串里，`\` 是**转义字符**，`".\apple.in"` 里的 `\a` 会被解释成别的字符，编译都可能过不去。
**改法**：**直接写文件名，不要带任何路径前缀**：

```cpp
freopen("apple.in", "r", stdin);      // ✓ 正确：就在当前目录
```

#### 错误 6：只写一个，另一个忘了

**症状**：读到了数据，但输出没写进文件（或者反过来）。
**原因**：只写了 `freopen("apple.in", "r", stdin);`，忘了输出那行。
**改法**：把两行当成一个整体背下来，**永远成对写**。

#### 错误 7：模式写反

**症状**：输出文件是空的，或者数据被清空。
**原因**：输入用 `"w"`，输出用 `"r"`。
**记法**：`r` = read = 读进来 = `stdin`；`w` = write = 写出去 = `stdout`。

#### 错误 8：注释掉了却忘了恢复

**症状**：本地调试时注释掉 `freopen` 方便看输出，交卷时忘了恢复 → 单题 0 分。
**改法**：**不要用"注释掉"这个办法**。始终保留 `freopen`，要看中间结果就用 `cerr` 输出到屏幕：

```cpp
cerr << "调试：" << n << '\n';   // cerr 不受 freopen(stdout) 影响，会打到屏幕
```

::: range 为什么用 `cerr` 而不是 `cout` 调试
`freopen("apple.out", "w", stdout)` 之后，**`cout` 的内容会进文件**，你在屏幕上什么都看不到。

`cerr` 对应 `stderr`，**你没有重定向它**，所以它会打到屏幕上——正好用来调试。

**注意：调试输出交卷前要删掉或注释掉**，虽然 `cerr` 不进答案文件，但会拖慢程序。
:::

#### 错误 9：用绝对路径

**症状**：本地能跑，评测机打不开文件。
**原因**：写了 `freopen("D:\\data\\apple.in", ...)`。
**改法**：**只用文件名**。评测机的工作目录就是你交的题目文件夹。

#### 错误 10：不检查 `freopen` 是否成功

**症状**：文件其实没打开，但程序继续跑，读到一堆垃圾值，最后输出一个"看起来有点道理"的错答案。
**原因**：`freopen` 失败时返回 `NULL`，但很多人不检查，于是问题被隐藏了。
**改法**：调试阶段加上检查，**这一行能帮你立刻定位问题**：

```cpp
if (freopen("apple.in", "r", stdin) == NULL) {
    cerr << "打不开 apple.in！\n";   // 屏幕上立刻能看到
    return 1;
}
```

::: exam 交卷前的文件关清单
- [ ] **每一题**的 `freopen` 文件名与题目要求**逐字符**一致（大小写、后缀）
- [ ] 输入是 `"r"` + `stdin`，输出是 `"w"` + `stdout`，两行都在
- [ ] 没有路径前缀，没有 `.\`，没有绝对路径
- [ ] 没有全角标点
- [ ] 调试用的 `cerr` 已删除或注释
- [ ] 没有"为了本地调试而注释掉的 `freopen`"
- [ ] 代码与题目**没有错位**（文件名、读的文件、输出格式三处都对上）
- [ ] 本地用**真实文件**跑过一遍，不是用键盘输入
:::

### 一个不容易想到的坑

::: pitfall 本地测试的假象
如果你在本地只用键盘输入测试，那 `freopen` 写错你**永远发现不了**——因为键盘输入和文件输入走的是不同的路。

**正确做法**：本地也建 `apple.in` / `apple.out` 两个文件，
把样例数据写进 `apple.in`，运行后打开 `apple.out` 比对。

**这一步是复赛前必须做的演练**，它同时验证了：文件名对不对、路径对不对、输出格式对不对。
:::

## 动手检查

1. 建一个 `apple.in`，写入两个数；用上面的模板程序运行，打开 `apple.out` 看结果。
2. 把 `freopen` 里的文件名故意改错（比如改成 `appel.in`），重新运行——观察程序是崩溃、还是输出垃圾值。
3. 在 `freopen` 后面加一行 `cout << "测试" << '\n';`，运行后检查：这句话跑到哪里去了？再把 `cout` 换成 `cerr`，看有什么不同。
4. 对照"十个真实现场"，逐条检查你自己的模板。
